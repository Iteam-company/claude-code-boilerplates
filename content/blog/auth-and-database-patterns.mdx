Two things trip up most developers building on this boilerplate for the first time: how the JWT flows through the app, and how Drizzle queries are structured. This post walks through both end to end.

## Authentication Flow

The auth system uses JWTs stored on the client. There is no session cookie, no NextAuth, no third-party provider — just a signed token returned on login and sent back on every request.

### Registration and Login

Both routes live in `app/api/auth/`. They call `userService.register` or `userService.login`, which returns a sanitized user object and a signed JWT:

```ts
const token = jwt.sign({ userId: user.id }, process.env.JWT_SECRET!, {
  expiresIn: '7d',
});
```

The token is returned in the response body — the client stores it in `localStorage` and attaches it to every subsequent request.

### Protecting a Route

Any route that requires a logged-in user calls `getUserFromRequest` at the top:

```ts
import { getUserFromRequest } from '@/lib/auth';

export async function GET(req: Request) {
  const user = await getUserFromRequest(req);
  // user is guaranteed here — throws 401 if token is missing or invalid
  const posts = await postService.getByAuthor(user.id);
  return Response.json(posts);
}
```

`getUserFromRequest` reads the `Authorization: Bearer <token>` header, verifies the signature, and returns the decoded user. If anything is wrong, it throws `HttpError(401)` which `handleError` converts into a proper JSON response.

### Ownership Checks

Ownership logic belongs in the service, not the route. The route passes the current user's ID; the service checks it:

```ts
// post.service.ts
async function deletePost(postId: string, requestingUserId: string) {
  const post = await postRepo.findById(postId);
  if (!post) throw new HttpError(404, 'Post not found');
  if (post.authorId !== requestingUserId) throw new HttpError(403, 'Forbidden');
  await postRepo.delete(postId);
}
```

Never perform ownership checks in the route handler. The service is the right place because it has access to the full entity.

### Sanitizing the User Object

Never return `passwordHash`. Strip it before sending any user data to the client:

```ts
const { passwordHash: _, ...safeUser } = user;
return Response.json(safeUser);
```

This pattern appears throughout the codebase. The `_` variable name signals intentional discard.

## Database Patterns with Drizzle

### Schema Definition

Tables live in `modules/[name]/[name].schema.ts`. Export names follow the `camelCase + Table` convention:

```ts
import { pgTable, text, timestamp, uuid } from 'drizzle-orm/pg-core';

export const postTable = pgTable('posts', {
  id: uuid('id').primaryKey().defaultRandom(),
  title: text('title').notNull(),
  content: text('content').notNull(),
  authorId: uuid('author_id')
    .notNull()
    .references(() => userTable.id, { onDelete: 'cascade' }),
  createdAt: timestamp('created_at').notNull().defaultNow(),
  updatedAt: timestamp('updated_at').notNull().defaultNow(),
});
```

After defining a schema, register it in `db/drizzle.ts` and `db/schema.ts`. The `drizzle-module` skill does this automatically.

### Relations

Every schema file needs a companion `*.relations.ts`. Without it, `db.query.*` with `with` will throw a runtime error:

```ts
// post.relations.ts
import { relations } from 'drizzle-orm';
import { postTable } from './post.schema';
import { userTable } from '../user/user.schema';

export const postRelations = relations(postTable, ({ one }) => ({
  author: one(userTable, {
    fields: [postTable.authorId],
    references: [userTable.id],
  }),
}));
```

Register the relations in `db/drizzle.ts` alongside the schema.

### Repository Queries

Repos live in `modules/[name]/[name].repo.ts`. Keep them simple and typed:

```ts
// Fetch a post with its author
async function findById(id: string) {
  return db.query.postTable.findFirst({
    where: eq(postTable.id, id),
    with: { author: true },
  });
}

// Insert a new post
async function create(data: NewPost) {
  const [post] = await db.insert(postTable).values(data).returning();
  return post;
}

// Paginated list
async function findMany(limit = 20, offset = 0) {
  return db.query.postTable.findMany({
    orderBy: desc(postTable.createdAt),
    limit,
    offset,
    with: { author: true },
  });
}
```

The `with` clause works only when relations are defined. If you see a `referencedTable` error, the `*.relations.ts` file is missing or not registered.

### Migrations vs Push

| Command               | When to Use                                       |
| --------------------- | ------------------------------------------------- |
| `npm run db:push`     | Dev only — sync schema without migration files    |
| `npm run db:generate` | Generate a SQL migration file from schema changes |
| `npm run db:migrate`  | Apply pending migration files to the database     |

For production, always use `generate` + `migrate`. For local development on a throwaway database, `push` is faster.

## Common Mistakes

**Querying without relations defined** — always create `*.relations.ts` alongside every `*.schema.ts`.

**Business logic in the route** — routes validate input and call the service. Nothing else.

**Returning `passwordHash`** — always destructure it out before responding.

**Using `parse` instead of `safeParse`** — `parse` throws; `safeParse` returns a result object. Always use `safeParse` so you control the error shape.

**Importing `Request` or `Response` in the service** — services must not know about HTTP. They receive plain values and return plain objects or throw `HttpError`.

> The discipline of keeping each layer's responsibility narrow is what makes this architecture scale. A route that does too much is the most common source of bugs and technical debt in Node.js apps.

The hardest part of an MVP is not the code — it is the decisions. This boilerplate eliminates the setup decisions so you can focus on the ones that actually matter: what the product does and for whom.

Here is a realistic 48-hour playbook.

## Friday Evening: Foundation (2–3 hours)

### 1. Clone and wire up the environment

Follow the Quick Start guide. By the end of this step you should have:

- The dev server running at `localhost:3000`
- A Neon database connected
- Auth working (`/register` and `/login` functional)

### 2. Define your data model on paper

Before writing a single line of code, sketch your entities and their relationships. For a simple task manager:

```
User → Project → Task
             ↘ Comment
```

Write out the fields for each table. Be conservative — an MVP needs the minimum that proves the idea, not every feature you can imagine.

### 3. Scaffold your modules

For each entity, run the skill in Claude Code:

```
/drizzle-module
```

Then: `Add a project module with fields: name (text), description (text nullable), authorId (FK to users)`

Repeat for every entity. Each invocation generates all 7 files. Push the schema to your database:

```bash
npm run db:push
```

## Saturday: Core Features (8–10 hours)

### 4. Build the API layer

For each module, add the routes you need. Use Claude Code:

> Use the nextjs-api-route skill to add:
>
> - GET /api/projects — list the current user's projects
> - POST /api/projects — create a project
> - DELETE /api/projects/[id] — delete a project (owner only)

Routes are thin by design. The service layer holds all business logic.

### 5. Add SWR hooks for each endpoint

```
/swr-hooks
```

> Add a useProjects hook for GET /api/projects and a useCreateProject mutation hook for POST /api/projects.

You now have typed, cached, auto-refreshing data fetching in one step.

### 6. Build the UI

This is the part that requires the most judgment. A few rules that keep it fast:

- Use Shadcn components for everything interactive — forms, dialogs, tables, buttons
- Use `Card` + `Badge` for list items
- Use `Dialog` for create/edit flows — no separate pages until you need them
- Mobile-first, but do not obsess over responsive layout on day one

For each page, let Claude Code scaffold the component structure:

> Create a ProjectsPage server component that fetches projects and renders a ProjectList client component. The list shows each project's name, description, and a delete button.

### 7. Connect auth to the UI

The `getUserFromRequest` helper is already in `lib/auth.ts`. In API routes, it throws a `401` automatically if the token is missing. On the client, store the JWT in `localStorage` and attach it via the `fetcher` utility.

The `useUser` hook (in `hooks/api/useUser.ts` if you generated it) gives you the current user anywhere in the component tree.

## Saturday Evening: Polish (2–3 hours)

### Error and loading states

Every page needs three states: loading skeleton, error message, and the actual content. Claude Code generates these alongside the hook:

> Add loading and error states to the ProjectList component using the Shadcn Skeleton component for loading.

### Toast notifications

Wrap every mutation's `onSuccess` and `onError` with `toast.success` and `toast.error` from Sonner. It is already installed — just import it:

```ts
import { toast } from 'sonner';
```

### Form validation messages

Zod schema errors surface automatically through React Hook Form. Make sure every `FormField` has a `FormMessage` component below it — that is all you need.

## Sunday: Deploy and Share (2–3 hours)

### 8. Deploy to Vercel

```bash
npx vercel
```

Follow the prompts. Then push your environment variables:

```bash
vercel env add DATABASE_URL
vercel env add JWT_SECRET
vercel env add NEXT_PUBLIC_BASE_URL
```

Set `NEXT_PUBLIC_BASE_URL` to your Vercel deployment URL.

### 9. Run your first migration in production

Your Neon database is already accessible from Vercel — same `DATABASE_URL`. The `db:push` you ran locally already applied the schema, so no extra step is needed unless you change the schema after deployment.

### 10. Share the link

That is the MVP. Send it to your first five users.

## What to Skip on Day One

These are all fine ideas — after you have users:

- Image uploads (add with the `cloudinary-upload` skill later)
- Email notifications
- Admin dashboard
- Pagination (return all results, add a `limit` later)
- Dark mode customization (it already works via `next-themes`)
- Unit tests

> An MVP is a question, not a product. Build only enough to get an answer, deploy it, and let real usage tell you what to build next.
